1. The whole deck in 30 seconds

A CPU is a few very smart workers. A GPU is a stadium of thousands of simpler workers. For work that can be split into thousands of identical little jobs, the stadium wins by a landslide — that's why GPUs are used for AI, simulations, image processing, crypto.

The problem: those thousands of workers are on a different chip with its own memory. So to use them you must:

  1. Copy your data over to the GPU's memory.
  2. Tell thousands of GPU threads to run the same small function (called a kernel) — each thread handles one little piece of the data.
  3. Copy the results back.

That's it. That's CUDA. The rest of the deck is just the details of those three steps: how you launch the threads (<<<blocks, threads>>>), how each thread figures out which piece of data is mine (threadIdx.x + blockIdx.x * blockDim.x), and how threads combine their answers safely (shared memory, __syncthreads(), atomicAdd()).

If you only remember one sentence

CUDA is normal C running on the CPU that occasionally ships data to the GPU, launches a function across thousands of GPU threads at once, and ships the answers back.

3. Why GPUs exist (slides 2–8) — the motivation part

These slides are building one argument: CPUs got fast at doing one thing at a time, but they stopped getting faster; GPUs got fast at doing millions of things at once.

GPU
Graphics Processing Unit — a chip built to draw 2 million pixels, 60 times a second. Drawing pixels means: do the same little math to a huge pile of numbers, all at once. That's exactly what scientific computing and AI need too.
GPGPU (slide 7)
“General-Purpose computing on a GPU” — using the graphics chip for non-graphics math: machine learning, simulations, medical imaging, crypto mining, Monte-Carlo finance. The slide lists these as typical applications.
GFLOPs / FLOPS (slide 3)
A speed unit, like “liters per second” for a pump. FLOPS = FLoating-point Operations Per Second. GigaFLOPS = billions per second; 1000 GFLOPs = 1 TFLOP. MIPS = millions of instructions per second (frequency ÷ cycles-per-instruction).
Heterogeneous computing (slide 5)
Fancy phrase for “CPU and GPU working together”. CPU = host, piloting the program; GPU = co-processor, doing the heavy lifting.
The numbers to remember (slide 5)
An RTX 3080 has 8,704 CUDA cores in 68 SMs — i.e. 68 clusters of 128 little cores each. A CPU has 8 or 16 cores. That's the whole story of why GPUs are fast.
History (slides 3–4)
The idea came out of the PS3's Cell processor (2006) and PC gaming GPUs. NVIDIA released CUDA in 2007 — the software that made GPUs programmable in a C-like language instead of graphics-only tricks.
Slide 6 — the three vocabulary words

Thread = one worker. Block = a team of workers that can share notes. Grid = all the teams you launched. Keep this hierarchy in your head; everything else is built on it.

4. Two computers in one (slides 2, 10, 14–15)

This is the single biggest source of confusion for beginners, so read it twice:

The CPU and GPU are two separate computers with two separate memories. They do not share RAM.

The 6-line pattern that every CUDA program follows (slide 21 spells this out)

Why beginners get crashes

A host pointer (from malloc) and a device pointer (from cudaMalloc) are both just int* to the compiler, but they point into different memories. If you accidentally pass a host pointer to a kernel, the GPU will happily read garbage from an address that means nothing to it — and your program dies with an unhelpful “illegal memory access”. Always keep the dev_ prefix convention from the slides.

5. Anatomy of a kernel (slides 11–13)

Slide 11 lists what CUDA adds to plain C. Here it is, translated:

a) Function qualifiers — “where does this function run?”

Written asRuns onCallable fromIn plain English
__global__ void KernelFunc()GPUCPUA kernel. Launched from the CPU, runs on the thousands of GPU threads.
__device__ float DeviceFunc()GPUGPU onlyA helper the kernel calls. The CPU can't call it.
(no qualifier) float HostFunc()CPUCPUNormal C. main is one of these.

b) Variable qualifiers — “where does this variable live?”

__shared__ (shared by a team of threads, fast — see section 9), __constant__, __device__ for variables. Don't panic about these yet; __shared__ is the only one you need early.

c) The launch syntax <<<…>>> — “how many workers, and how are they grouped?”

kernel<<< number_of_blocks , threads_per_block >>>( arguments );

Triple angle brackets = “this call goes to the GPU”. This is the line that turns one function call into thousands of simultaneous executions.

d) The four built-in variables (slide 11)

Inside a kernel, these are magically available so each thread knows who it is:

VariableAnswersExample value
threadIdx.x“What's my seat number inside my team?”0 … blockDim.x-1
blockIdx.x“Which team am I in?”0 … gridDim.x-1
blockDim.x“How many seats per team?”e.g. 256
gridDim.x“How many teams total?”e.g. 512

Each of these also has .y and .z versions (for 2D/3D data like images), but every example in your deck uses .x. Start with .x.

Hello World with a kernel (slide 13) — read it slowly

__global__ void kernel( void ) { }          // runs on GPU, does nothing

int main( void ) {
    kernel<<< 1, 1 >>>();                // launch 1 block × 1 thread
    printf( "Hello, World!\n" );        // this line runs on the CPU!
    return 0;
}

Three things worth noticing, because they're exactly the things that confuse people:

  • <<<1, 1>>> means 1 block containing 1 thread. So no parallelism yet — this program computes nothing. It exists only to show you the mechanism.
  • The printf runs on the CPU, because only the empty kernel was sent to the GPU. (A printf inside a kernel would print from the GPU.)
  • The empty function body is not a mistake: the point of the example is that “this function was executed on the GPU, and here's the syntax that made it happen.”

Also note slide 13's remark: nvcc (NVIDIA's compiler) splits your file in two — it compiles the __global__ functions for the GPU and hands the rest to your normal C compiler (gcc / MSVC). That's why CUDA C is “just C” with a couple of extra keywords.

Adding two numbers on the GPU (slides 14–15)

__global__ void add( int a, int b, int *c) {
    *c = a + b;
}

Why does c have a star and the others don't? This is the “pass by value vs pass by pointer” line the slide points out. a and b are passed by value: the numbers themselves are copied to the GPU, no problem. But a computed result must be written somewhere — and the only memory the GPU can write to is GPU memory. So c must be a device pointer. Rule of thumb: data in = by value results out = pointer to device memory.

Then main looks like this (this is the pattern; section 2 of the guide above shows the 6 steps it follows):

int a, b, c;                       // HOST copies
int *dev_a, *dev_b, *dev_c;        // DEVICE copies (different memory!)
int size = sizeof(int);

cudaMalloc( (void**)&dev_a, size );      // "malloc", but on the GPU
cudaMalloc( (void**)&dev_b, size );
cudaMalloc( (void**)&dev_c, size );

cudaMemcpy( dev_a, &a, size, cudaMemcpyHostToDevice );   // ship inputs over
cudaMemcpy( dev_b, &b, size, cudaMemcpyHostToDevice );

add<<< 1, 1 >>>( dev_a, dev_b, dev_c );      // 1 block, 1 thread

cudaMemcpy( &c, dev_c, size, cudaMemcpyDeviceToHost );   // bring result back

cudaFree( dev_a ); cudaFree( dev_b ); cudaFree( dev_c ); // "free", but on the GPU

The mapping to ordinary C is the whole point of slide 14:

Ordinary CCUDAMeaning
malloccudaMallocReserve memory on the GPU
freecudaFreeRelease GPU memory
memcpycudaMemcpyCopy — but now you must say which direction: HostToDevice or DeviceToHost
A detail that bites everyone

cudaMemcpy's third argument is a number of bytes, not elements. For one int it's sizeof(int) = 4. For an array of N ints it's N * sizeof(int). Mixing those up is the #1 silent bug in student CUDA code (and yes, the deck's array examples show sizeof(int) — see section 10).

6. Threads, blocks, grids — how the GPU gets organized (slides 5–6, 16–21)

Slide 5 says it directly: “Unlike the threads and processes of UPC/OpenMP and MPI, CUDA adds extra layers of organization of the threads”. Here's the hierarchy:

The two ways the deck introduces parallelism

7. The index formula, finally explained (slide 20)

int index = threadIdx.x + blockIdx.x * blockDim.x;

This one line terrified you, didn't it? It's just P.E. class attendance:

The classroom analogy

Imagine a class of 512 students, seated in rows (blocks) of 16. How do you compute a student's overall position in the class?
“All the full rows before my row, plus how far along I am in my own row.”

index = threadIdx.x + blockIdx.x * blockDim.x
= my seat in my row + my row number × seats per row.

The trap in the formula

blockDim.x is written with a capital D and no “s” after D — don't type blockdims.x or blockDim. And threadIdx/blockIdx restart at 0 for every block: thread 0 of block 3 and thread 0 of block 7 both have threadIdx.x == 0. Multiplying by blockDim.x is what makes each block cover a different stretch of the array.

And the launch that goes with it (slide 21):

// N elements, T threads per block → N/T blocks of T threads = N workers total
add<<< N/T , T >>>( dev_a, dev_b, dev_c );
Reading a launch line out loud

add<<<512, 256>>>(...) is read as: “Run add on the GPU as 512 blocks of 256 threads” = 131,072 executions of that function, all at once. The function body is written as if for one thread — the launch line is what multiplies it.

8. Every code example, line by line

8.1 Vector addition with blocks only (slides 16–17, vecadd0.cu)

__global__ void add( int *a, int *b, int *c ) {
    c[blockIdx.x] = a[blockIdx.x] + b[blockIdx.x];
}
// launched as: add<<< N, 1 >>>( dev_a, dev_b, dev_c );  →  N blocks, 1 thread each

How it works: <<<N, 1>>> creates N blocks. Each block runs add once (since there's only 1 thread per block), and each block finds its own slot in the array through blockIdx.x — block 7 adds element 7. So different blocks handle different data. Multiply the number of workers, and the array gets chewed through in parallel.

Why it's still weak: 1 thread per block. Real GPUs schedule work in blocks of (up to) 1024 threads, so a block of one thread is like taking a bus to deliver one letter.

8.2 Vector addition with threads only (slide 18, vecadd1.cu)

__global__ void add ( int *a, int *b, int *c ) {
    c[threadIdx.x] = a[threadIdx.x] + b[threadIdx.x];
}
// launched as: add<<< 1, N >>>( dev_a, dev_b, dev_c );  →  1 block, N threads

Same idea, different index: now the block has N threads and each thread handles one element via its seat number, threadIdx.x. (Remember slide 19: this caps you at 1024 elements.)

8.3 The real version — blocks and threads (slides 20–21)

__global__ void add( int *a, int *b, int *c) {
    int index = threadIdx.x + blockIdx.x * blockDim.x;
    c[index] = a[index] + b[index];
}
// #define N 512, #define THREADS_PER_BLOCK 256  → 512/256 = 2 blocks of 256
add<<< N/THREADS_PER_BLOCK, THREADS_PER_BLOCK >>>( dev_a, dev_b, dev_c );

This is the one to memorize — it's the pattern every large CUDA project uses, just generalized. If you can write this from memory and explain the index line, you've passed the most technical part of this course.

8.4 The dot product — the “interesting” example (slides 22–25)

Vector addition was easy because each output needed exactly one thread. A dot product is different: it produces one single number from N products. So thousands of threads must compute tiny pieces and then combine them into one result. That's what slides 22–25 are really about: thread cooperation.

// Step 1 (slide 22): each thread makes ONE product — but now what?
__global__ void dot ( int *a, int *b, int *c ) {
    int temp = a[threadIdx.x] * b[threadIdx.x];   // a partial answer… then?
}

Everyone computed a product; nobody can see anyone else's product (each thread's temp is private). The slide's question — “How to compute the final sum?” — is the whole challenge.

Step 2 (slides 23–24): let the threads share a whiteboard. CUDA gives each block a small, extremely fast, on-chip scratchpad called shared memory, declared with __shared__. Threads in the same block can all read and write it, so they can drop their partial products there and one thread can add them up:

__global__ void dot( int *a, int *b, int *c ) {
    __shared__ int temp[N];                            // a whiteboard per BLOCK
    temp[threadIdx.x] = a[threadIdx.x] * b[threadIdx.x];  // everyone posts their product
    __syncthreads();                                // WAIT until every teammate has posted
    if( 0 == threadIdx.x ) {                        // ONE thread does the summing
        int sum = 0;
        for( int i = 0; i < N; i++ ) sum += temp[i];
        *c = sum;                                    // write the final answer
    }
}

The two new ideas, in plain words:

  • __syncthreads() = “everybody stop here until the whole team has caught up.” Without it, thread 0 might start summing before other threads have written their values — it would read uninitialized garbage. This barrier only works within a block; it can't synchronize different blocks.
  • Why only thread 0 sums? Because the 1,000 threads would otherwise all compute the same sum and all write *c — a thousand redundant writes to the same spot, racing each other. Letting one thread do the final loop is simple and correct (a real optimization would have threads sum in a tree, but the deck keeps it simple).

9. The hard part: race conditions and atomics (slide 25)

Slide 24 ends with a complaint: “Launching with one block will not utilize much of the GPU.” True — a single block of N threads leaves most of the stadium empty. So slide 25 goes multi-block:

// slide 25's idea: EACH BLOCK computes a partial sum of its own chunk
dot<<< N/THREADS_PER_BLOCK, THREADS_PER_BLOCK >>>( dev_a, dev_b, dev_c );

Now every block has its own temp[] whiteboard, computes its own local sum… and then all of them want to add that partial sum into the single global variable *c:

*c += sum;   // ???

Why this line is dangerous: the race condition

*c += sum is secretly three operations: (1) read *c, (2) add sum, (3) write back. If two blocks do this at the same instant:

TimeBlock 0Block 1Value of *c
t1reads *c → 100100
t2reads *c → 100100
t3writes 100+5 → 105105
t4writes 100+7 → 107107 ✗ (should be 112)

Block 0's contribution was silently overwritten. The answer is wrong, and it's wrong only sometimes — depending on timing. That's the nightmare property of races: they pass your tests on your machine and fail during the exam demo.

The fix: atomics (slide 25's list)

An atomic operation does read-modify-write as one indivisible step — no other thread can squeeze in between. CUDA provides them for exactly this:

atomicAdd(c, sum);   // "add sum to *c, and don't let anyone interrupt you"

The slide lists the whole family: atomicAdd() atomicSub() atomicMin() atomicMax() atomicInc() atomicDec() atomicExch() atomicCAS() — you add, subtract, take min/max, increment, decrement, exchange, and compare-and-swap, all safely. atomicAdd is the one you'll actually use for reductions like this.

Two gotchas the slide doesn't spell out

1. Slide 25's code still writes *c = sum — if you literally run multi-block code with *c = sum, blocks overwrite each other's partial sums entirely. The correct multi-block code uses atomicAdd(c, sum). 2. The result accumulator must start at zero before the kernel runs (cudaMemset(dev_c, 0, sizeof(int)) or copy a 0 over), or you're adding onto whatever garbage was in that memory.

The corrected multi-block dot product

__global__ void dot( int *a, int *b, int *c ) {
    __shared__ int temp[THREADS_PER_BLOCK];
    int index = threadIdx.x + blockIdx.x * blockDim.x;   // ← global index (slide 20)
    temp[threadIdx.x] = a[index] * b[index];                // my chunk's product
    __syncthreads();                                        // wait for my block
    if( 0 == threadIdx.x ) {
        int sum = 0;
        for( int i = 0; i < THREADS_PER_BLOCK; i++ ) sum += temp[i];
        atomicAdd( c, sum );   // one safe add per block — no race
    }
}
// in main: cudaMemset(dev_c, 0, sizeof(int)); then launch dot<<<N/THREADS_PER_BLOCK, THREADS_PER_BLOCK>>>

Full runnable version with error-free main(): see code/dot_product.cu in this workspace.

These two slides have no code; they're asking “what does the word thread / core / process / task mean in each programming model?” Here's the whole thing as one table:

12. Beginner-mistake cheat-sheet

  • Passing a host pointer to a kernel. Wrap-up: any pointer that a kernel dereferences must come from cudaMalloc. Result of the mistake: “illegal memory access” crash.
  • Bytes vs elements. cudaMemcpy(dst, src, N*sizeof(int), ...) — not sizeof(int).
  • Forgetting to copy results back. The GPU's memory dies with cudaFree; your host array never updates unless you cudaMemcpy DeviceToHost.
  • Reading c on the host right after launching. The launch is asynchronous-ish and the results are in device memory. Copy back first, then print.
  • Assuming blocks run in order. They don't. Never write code that depends on block 3 finishing before block 4.
  • Using __syncthreads() to guard data shared across blocks. It only synchronizes within one block. Across blocks: atomics, or launch a second kernel.
  • Missing the if (threadIdx.x == 0) on the final write. If all threads write the same scalar, you're back to race conditions.
  • Block size not dividing N. N/THREADS_PER_BLOCK truncates; guard the tail with if (index < N) (see the runnable code in code/).
  • Forgetting to initialize the atomic accumulator to zero.

13. Self-check quiz

Answer before opening each one. If you can do all nine, you understand this deck better than most of the class.

1. What's the difference between __global__ and __device__?

__global__ functions are kernels: launched from the host (CPU), run on the device (GPU), and called with the <<<...>>> syntax. __device__ functions run on the GPU too, but are callable only from other GPU code — helper functions the kernels use. (Slide 11's table.)

2. Why can't a kernel just read your int a[100] from main?

Because the GPU has its own memory. The host array lives in CPU RAM, which isn't accessible to GPU threads. You must cudaMalloc a device array and cudaMemcpy the data over first.

3. add<<<4, 8>>>(...) — how many executions of add, and what global index does thread 3 of block 2 compute (with blockDim.x = 8)?

4 × 8 = 32 executions. Index = threadIdx.x + blockIdx.x*blockDim.x = 3 + 2*8 = 19.

4. Why is __syncthreads() needed in the dot product kernel?

Thread 0 sums temp[], but temp[] is filled by all threads. Without the barrier, thread 0 could reach the summing loop before other threads wrote their products, and it would add uninitialized values. __syncthreads() makes every thread in the block wait until all have finished their write.

5. What is a race condition, in one sentence? How does atomicAdd fix it?

A race condition is when two threads read-modify-write the same location concurrently, so one update gets lost (last writer wins). atomicAdd performs the read-add-write as a single indivisible operation, so the updates serialize correctly instead of clobbering each other.

6. What are the three CUDA memory spaces in slide 6, and how do they compare?

Global: visible to all threads, large but slow. Shared: visible only inside one block, small but very fast (on-chip). Registers: private to each thread, fastest of all. (Think: warehouse → team whiteboard → your own notepad.)

7. Why does the deck go from “1 block of N threads” (slide 24) to “N/T blocks of T threads” (slide 25)?

Because a single block can't occupy the whole GPU — blocks are capped at (typically) 1024 threads and the GPU has many SMs. Many blocks → real parallelism. But then multiple blocks must combine their partial sums, which introduces the race condition that atomics solve.

8. Why do a and b get passed by value but c by pointer in add(int a, int b, int *c)?

Inputs can be copied over by value (the values are all the kernel needs). The output must be stored somewhere the GPU can write — and that's only device memory — so the kernel needs the address of a device variable: a device pointer.

9. Which model matches: “processes with private memory that communicate by message passing”?

MPI. UPC uses threads with a global shared address space; CUDA uses (GPU) threads organized in blocks/grids. (Slides 26–27.)

14. Glossary

Host
The CPU and its memory. Your normal C program lives here.
Device
The GPU and its memory (VRAM). Kernels live here.
Kernel
A __global__ function — the unit of work you ship to the GPU. Launched with <<<blocks, threads>>>.
Thread
The smallest unit of execution; one “worker” running the kernel body once.
Block
A team of threads that can share __shared__ memory and be synchronized with __syncthreads().
Grid
All blocks of one kernel launch.
SM (Streaming Multiprocessor)
A cluster of CUDA cores on the chip (e.g. 68 SMs × 128 cores on the RTX 3080). Blocks get assigned to SMs by the hardware scheduler.
Global memory
GPU's main VRAM. All threads can touch it; biggest and slowest.
Shared memory
Fast on-chip scratchpad, one per block, declared __shared__.
Registers
Per-thread ultra-fast storage (where int temp etc. live).
cudaMalloc / cudaFree
GPU versions of malloc / free.
cudaMemcpy
Copies between host and device; you must state the direction (HostToDevice / DeviceToHost).
cudaMemset
Fills device memory with a byte value — handy to zero an accumulator.
__syncthreads()
Barrier inside a block: all threads wait until everyone arrives.
Atomic operation
An indivisible memory update (e.g. atomicAdd) that is safe under concurrency.
Race condition
A bug where the result depends on the timing of concurrent threads.
Reduction
Turning many values into one (dot product, sum, max) — the classic pattern requiring cooperation.
GPGPU
General-Purpose computing on GPUs: using graphics chips for non-graphics math.
GFLOP/s
Billions of floating-point operations per second; the usual way to quote GPU throughput.
nvcc
NVIDIA's CUDA compiler: splits your file into GPU code and ordinary C code.
